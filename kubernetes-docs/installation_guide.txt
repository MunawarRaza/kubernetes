Point 2. ====
1. Configure containerd
	1. Configure systemd driver in containerd
		sudo mkdir -p /etc/containerd
		containerd config default | sudo tee /etc/containerd/config.toml
	2. Enable SystemdCgroup
		sudo vi /etc/containerd/config.toml
		# find
			SystemdCgroup = false
		# Change it to:
			SystemdCgroup = true
	3. Restart containerd:
		sudo systemctl restart containerd

2 Disable swap
	sudo swapoff -a	

3. Load required kernel modules
cat <<EOF | sudo tee /etc/modules-load.d/k8s.conf
overlay
br_netfilter
EOF

	sudo modprobe overlay
	sudo modprobe br_netfilter

	Note:
		- /etc/modules-load.d/k8s.conf this file tells linux "Whenever the system boots, automatically load these kernel modules."
		- A kernel module is like a plugin for the Linux kernel. Instead of compiling every feature into the kernel, Linux can load functionality only when it's needed.
		Module 1: overlay
		- modprobe overlay --> This loads the Overlay Filesystem driver.
			Container runtimes (containerd, Docker, CRI-O) don't create a full copy of an image for every container. Instead, they use layered filesystems. Suppose an Ubuntu image contains:
			/
			├── bin
			├── etc
			├── lib
			When you create 100 containers, containerd doesn't duplicate the entire filesystem 100 times. Instead, it uses:
				Read-only Image Layer
						+
				Writable Container Layer
						=
				Merged Filesystem
			This is implemented by OverlayFS. This module is required by containerd's default overlayfs snapshotter.
		Example:
			Lower Layer (Image)
			-------------------
			/etc/passwd
			
			Upper Layer (Container)
			-----------------------
			/tmp/file.txt
			
			Merged View
			-----------------------
			/etc/passwd
			/tmp/file.txt
		Module 2: br_netfilter
		- modprobe br_netfilter --> This one is more Kubernetes-specific.
		- Imagine two Pods on the same node.
			Pod A
			│
			│
			Linux Bridge (cni0)
			│
			│
			Pod B
		Traffic flows through a Linux bridge. Without br_netfilter, packets crossing the bridge bypass those rules. Normally, Linux does not send bridged traffic through iptables. That becomes a problem because Kubernetes relies heavily on iptables (or nftables via compatibility) for:
			Services
			Network Policies
			kube-proxy rules
			CNI plugins
			
		Loading this module allows bridged traffic to be inspected by the firewall framework, enabling Kubernetes networking features to work correctly.

4. Configure sysctl
cat <<EOF | sudo tee /etc/sysctl.d/k8s.conf
net.bridge.bridge-nf-call-iptables=1
net.bridge.bridge-nf-call-ip6tables=1
net.ipv4.ip_forward=1
EOF

	sudo sysctl --system
	
	Note:
	- sysctl changes Linux kernel parameters at runtime. You can check active and inactive with sysctl -a
	- Linux can behave in two ways to route the traffic. 
		1. Host mode (default)
			Packet arrives --> Destination = this machine --> Accept
			or
			Packet arrives --> Destination = another machine --> Drop
			Linux does not forward packets by default.
		2. Router mode 
			- when we enable net.ipv4.ip_forward=1
				- Linux becomes capable of forwarding packets. 
				- Packet arrives --> Destination somewhere else --> Forward it
				  This is exactly what Kubernetes nodes do.
				- The node must forward packets between interfaces. Without IP forwarding, inter-pod communication across nodes would fail.
			
			net.bridge.bridge-nf-call-iptables = 1 
				- This works together with the br_netfilter module. It tells Linux: "When packets cross a bridge, pass them through iptables."
				- Without it Pod A --> Bridge --> Node B --> iptables never sees packet
				- Withit Pod A --> Bridge --> iptables --> Pod B
				- This enables Service load balancing and many CNI features.

Why we need point 4 and 5

		For that packet to succeed:
		
		1. The container filesystem needs OverlayFS (overlay).
		2. Bridged packets must be visible to firewall rules (br_netfilter).
		3. Bridged packets must actually be sent through iptables (bridge-nf-call-iptables / bridge-nf-call-ip6tables).
		4. The node must forward packets between interfaces (ip_forward).
		
		If any of these pieces are missing, you can encounter issues such as:
		
		1. Pods on different nodes cannot communicate.
		2. Kubernetes Services fail to route traffic correctly.
		3. NetworkPolicies are not enforced as expected.
		4. Container runtimes cannot use the default OverlayFS storage driver efficiently.

Point 3. ====
1. Set SELinux to permissive mode:
	# Set SELinux in permissive mode (effectively disabling it)
	sudo setenforce 0
	sudo sed -i 's/^SELINUX=enforcing$/SELINUX=permissive/' /etc/selinux/config
2. add repo
	# This overwrites any existing configuration in /etc/yum.repos.d/kubernetes.repo
cat <<EOF | sudo tee /etc/yum.repos.d/kubernetes.repo
[kubernetes]
name=Kubernetes
baseurl=https://pkgs.k8s.io/core:/stable:/v1.36/rpm/
enabled=1
gpgcheck=1
gpgkey=https://pkgs.k8s.io/core:/stable:/v1.36/rpm/repodata/repomd.xml.key
exclude=kubelet kubeadm kubectl cri-tools kubernetes-cni
EOF

3. Install kubelet, kubeadm and kubectl:
	sudo yum install -y kubelet kubeadm kubectl --disableexcludes=kubernetes
		here --disableexcludes=kubernetes means don't update the kubeadm kubelet and kubectl when we execute yum update command

4. (Optional) Enable the kubelet service before running kubeadm:
	sudo systemctl enable --now kubelet
	
	Note:
	The kubelet is now restarting every few seconds, as it waits in a crashloop for kubeadm to tell it what to do.

Point 4. ====

# Initialize
kubeadm init [flags]

Options
	--apiserver-advertise-address string (10.130.21.31)
	--apiserver-bind-port int32     Default: 6443
	--control-plane-endpoint string
	--pod-network-cidr string (10.95.0.0/16)
	--service-cidr string     Default: "10.96.0.0/12" (10.96.0.0/16)
	-service-dns-domain string     Default: "cluster.local"


	Note:
		- --apiserver-advertise-address --> The IP address of the control plane node that the kube-apiserver advertises to other Kubernetes components (kubelets, controller-manager, scheduler, etc.). This should be the IP address of the network interface through which other nodes can reach the control plane.
		- --pod-network-cidr string --> The CIDR block from which the CNI plugin allocates IP addresses to Pods.
		- --service-cidr string --> The CIDR block from which Kubernetes allocates virtual ClusterIP addresses to Services.
	
		For --pod-network-cidr and --service-cidr, you can choose almost any valid private CIDR block, provided it does not overlap with each other or with any existing networks (such as your node network, corporate LAN, VPN, or other routed networks). Also ensure the chosen Pod CIDR is compatible with your CNI plugin's configuration.
https://kubernetes.io/docs/reference/setup-tools/kubeadm/kubeadm-init/
